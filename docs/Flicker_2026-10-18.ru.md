## 19.10: проход, где появляется светлая вспышка

Инструмент: `BB_PASS_DUMP=адрес,...` + `BB_PASS_DUMP_TRIGGER` (`BB_PASS_DUMP_STEP`): каждая N-я
строка выбранных целей рендера перед проходом в display buffer; скрипт
`out/dev/flicker-laurence-pass.py`. Такой объём дефект не прячет.

Цепочка пост-обработки (захват кадра, `cap-1`): #90 (2560×1080 RGBA16F → 0x10791e0000; читает
HDR-сцену 0x1083110000, R32F 0x10822c0000, 1×1 0x106f001700; draw 1 — квад vs 0b0acf50 /
ps ccbf44a6, draw 2 — треугольник vs 4c37ae6d / ps bf368417 с константами 4112 байт из кольца CE)
→ #91, #92, #93 → #94 тонмаппинг в 0x10653f0000 → UI → копия в display buffer.

**Светлая вспышка впервые появляется на выходе #90** (2 поимки из 2): вход 0x1083110000 целый,
выход — правая нижняя четверть сцены в левой верхней четверти 1:1, остальное RGB 0,3765
(96/255) с меняющейся альфой. Это картина треугольника draw 2 с viewport, сдвинутым на
(−W/2, −H/2). Тёмная вспышка в #90 не видна — возникает позже (не локализована).

Для #90 на кадрах со вспышкой одинаковы: константы (снимок stage A, `BB_TRACE_CB_LIST`),

## 19.10: причина найдена — push-константы затирает compute окклюзии

Дампы перед каждым draw в 0x10791e0000 (`q`; дамп сам закрывает проход, поэтому `q` бывает
перед draw 1 и перед draw 2) показали: на кадре со светлой вспышкой сдвиг уже есть **после
draw 1** — квада vs 0b0acf50 / ps ccbf44a6. Этот draw идёт с clip disabled (`BB_DISPLAY_WATCH`
+ `BB_DISPLAY_WATCH_TARGET=10791e0000`): позиция считается в шейдере из push-констант
`(pos * xscale + xoffset) / 8192 - 1`, на CPU push всегда 1280,1280,-540,540. Сдвиг ровно на
(−W/2, −H/2) — это xoffset = yoffset = 0 при правильных xscale/yscale, то есть затёрты
первые 8 байт push-констант.

Порядок записи в `Rasterizer::BeginDraw` был: `BindResources` (push-константы) →
`scheduler.BeginRendering` → `CarrySuspend(false)` → `OcclusionQueries::Suspend` → `Resolve()`
— compute-dispatch с `pushConstants {count, num_events}` (8 байт со смещения 0) → draw.
В RADV (и по спецификации при несовместимых layout) push-константы одни на compute и graphics,
поэтому draw получал целые count/num_events как float ≈ 0. `Resolve` записывается не на каждом
проходе (есть ожидающие результаты окклюзии или кончаются слоты), отсюда одиночные кадры и
зависимость от того, насколько stage A опережает GPU (`BB_EXP_CONSTRAM_FINISH` менял тайминг).

Исправление: `BindResources` перенесён после `scheduler.BeginRendering` (внутри прохода compute
не записывается). Тот же механизм бьёт любой draw с clip disabled в начале прохода — вероятно,
и тёмный вариант (display copy vs 89cda9e4 тоже clip disabled).

Проверка (`run.sh`, бег до босса, `--move 20`): 6 прогонов из 6 без вспышек — ни светлых,
ни тёмных (`pc-1`…`pc-6`); до исправления вспышки были в большинстве прогонов. FPS тот же.
Диагностику из этого разбора перед релизом убрать (список выше + `BB_DISPLAY_WATCH_TARGET`,
`BB_PASS_DUMP_AT`, `BB_TRACE_PIPELINE`, `BB_TRACE_GPU_INPUTS`, `BB_EXP_*`).
