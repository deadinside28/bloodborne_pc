## Связь с текущими расследованиями

### Зависание до первого кадра: есть близкий отчёт на AMD

В [issue #216](https://github.com/deadinside28/bloodborne_pc/issues/216)
приложен [лог с RX 5500 XT](https://github.com/user-attachments/files/33536475/bbport-20261016_120626.log).
Я скачал его: Vulkan presenter создан, затем запускаются Core.Res-потоки,
после TaskManager остаётся только сообщение о ловушках записи под изображениями.
Автор не видит меню и не получает результата от переключения модели памяти.

Это полезное сходство с присланным зависанием на ноутбуке: искать только
специфическую неисправность NVIDIA уже недостаточно. Но лог #216 относится
к прежней линии renderer и не содержит снимка главного потока. Общая причина
с нашим случаем **не доказана**. Для сравнения нужны состояния диспетчера задач,
которые теперь снимает `scripts/diagnose_boot.gdb`.

Два похожих по названию исправления не стоит принимать за готовое решение:

- [PR #193](https://github.com/deadinside28/bloodborne_pc/pull/193) объясняет
  зависания при телепортах обрезанием указателя потока до 40 бит. В `testing`
  и локально уже есть `low_record()` с выделением низкой памяти. Кроме того,
  в том отчёте main спал на блокировке, а в нашем продолжает цикл с лимитером.
  Есть редкий незакрытый край: при отказе низкого выделения код возвращается
  к `calloc`; тогда контракт указателя снова не гарантируется. Без сообщения
  об отказе выделения связывать его с текущим зависанием оснований нет.
- [Комментарий в PR #138](https://github.com/deadinside28/bloodborne_pc/pull/138#issuecomment-6107606220)
  действительно разбирает чёрное окно. Но это утечка файловых дескрипторов
  после неудачного разрешения конфликта в Windows-ветке автора, с пределом UCRT.
  Автор отдельно указал, что upstream исправлять не требуется. Это другая причина.

| RIP=0 при старте bb-probe в новых отчётах | [#181](https://github.com/deadinside28/bloodborne_pc/issues/181), [#219](https://github.com/deadinside28/bloodborne_pc/issues/219), [#229](https://github.com/deadinside28/bloodborne_pc/issues/229) | Приоритетный незакрытый кластер; одинаковый RIP ещё не означает одинакового вызывающего |
| Сборка DLSS bridge без найденных headers | [#231](https://github.com/deadinside28/bloodborne_pc/issues/231) | Ошибка сборки из исходников, не доказательство причины краша готового AppImage |

В #229 сбой остаётся с `BB_DLSS=0`, старой моделью и отключёнными breadcrumbs.
Нельзя объявлять весь кластер исправленным наличием libcuda-fix. Наш отдельный
дамп, где нулевой вызов идёт из NVIDIA eglcore и падает даже vulkaninfo,
тоже требует самостоятельного сравнения окружения AppImage с хостом.

По #231 в `gpu/dlss_bridge/CMakeLists.txt` действительно нет собственного
`find_package(Vulkan)`; include передаётся вручную. При этом bridge получает
Vulkan proc-address функции через API инициализации. В отчёте непосредственно
доказано отсутствие заголовка. Добавление зависимости CMake разумно проверить
на Debian вне nix-shell, но связь с runtime RIP=0 пока остаётся предположением
комментатора, а не установленным фактом.

### Плавающие падения игры и катсцены

Есть хорошо связанный кластер: [#162](https://github.com/deadinside28/bloodborne_pc/issues/162),
[#169](https://github.com/deadinside28/bloodborne_pc/issues/169),
[#192](https://github.com/deadinside28/bloodborne_pc/issues/192).
Первый вариант пишет по NULL+8 в `+0x2199310`, второй передаёт NULL в memcpy
из `+0x21d5b40`. Обсуждение связывает оба с одним исчерпанным GX-аллокатором.

[PR #224](https://github.com/deadinside28/bloodborne_pc/pull/224) увеличивает
каждый из двух буферов команд с 256 KiB до 1 MiB. Локально я проверил оба
immediate в гостевом образе: там всё ещё 262144. Это актуальное небольшое
изменение, которое следует проверить в числе первых. Оно даёт запас,
но само не объясняет, почему буфер переполняется.

Это **другой heap**, чем наш кеш ресурсов катсцены Лоуренса: там было
160 MiB и локально стало 512 MiB. Увеличение одного не заменяет другого.
Наша private-clear правка PM4 при загрузке сохранения тоже исправляет отдельный
путь. Совпадение кода завершения 23 или 139 не объединяет эти причины.

[PR #214](https://github.com/deadinside28/bloodborne_pc/pull/214) выявил ещё
одну реальную дыру: в старой модели памяти не вызывается установка guest hooks.
Это подтверждается условием `GuestInPlace() && game && game->install_hooks`
и в `testing`, и локально. Теряются не только память-зависимые хуки, но и
защита GX-heap, aspect ratio и управление мышью. При переносе надо сохранить
разделение хуков по зависимости от модели и учесть наши новые хуки катсцены.

Отдельно [#207](https://github.com/deadinside28/bloodborne_pc/issues/207#issuecomment-6202536610)
разбирает exit 23 из Yebis motion blur: вызывающая функция допускает два
семпла, вызываемая требует минимум три. Автор ещё не установил, почему
выбрано два: повреждены таблицы либо индекс пасса не покрыт техниками.
Отключение motion blur предложено как обход; голое подавление assert
без проверки таблиц может скрыть первичное повреждение.

Прямого отчёта именно про Лоуренса в выгруженных issues и комментариях
не найдено. Есть [#180](https://github.com/deadinside28/bloodborne_pc/issues/180)
с испорченными текстурами во вступлении Амелии; это кандидат для сравнения
записи/аллокаторов, а не подтверждение одной причины.

## Как упорядочить issues

1. Разделить crash signatures: стадия, поток, RIP/guest offset, последняя
   assert-строка, модель памяти и версия renderer. Один exit code для этого
   непригоден: #111, #144, #173 и #207 завершаются через разные механизмы.
2. Собрать кластеры с главным техническим отчётом: GX heap (#162/#169/#192),
   VRAM (#142/#163/#173/#200), startup RIP=0, startup без первого кадра,
   Yebis (#207). Остальные связывать, сохраняя различия сигнатур.
3. Для уже включённых идей PR указывать commit/ветку/первую сборку. Все 19
   закрытых PR в снимке имеют merged_at=null: GitHub-merge не выполнялся;
   это само по себе ничего не говорит о ручном переносе их идей.
4. Отдельно помечать сторонние Windows-сборки и legacy CPU: например,
   [#232](https://github.com/deadinside28/bloodborne_pc/issues/232) и
   [#230](https://github.com/deadinside28/bloodborne_pc/issues/230) нельзя
   использовать как доказательство регрессии официального Linux AppImage.
   При этом дамп Windows из #162 полезен для подтверждения общего GX-аллокатора.
5. Учитывать последние опровержения. В
   [#182](https://github.com/deadinside28/bloodborne_pc/issues/182#issuecomment-6180049311)
   автор отозвал свою раннюю теорию и связал артефакты с RADV/HTILE на конкретном
   Oberon APU. Не нужно чинить по старой гипотезе texture cache и применять
   его nohiz-обход всем GPU.
6. После проверки текущей сборки пересмотреть устаревшие запросы ultrawide,
   DLC, FSR assets, языков и --play. Наличие функции не доказывает, что
   любая связанная проблема уже исправлена; закрывать только подтверждённый случай.

Практический порядок работ: сначала устойчивость и диагностика (#224/#214/#211,
