# Четырёхстадийный конвейер команд: измерения и этапы (18.10.2026)

Идея (запрос пользователя): разбить двухстадийный конвейер (`vk_draw_pipe.h`, stage A —
декодер, stage B — запись draw) на четыре стадии:

1. приём потока команд (декодер);
2. параллельное разрешение ресурсов на N потоках;
3. упорядоченный лёгкий поток барьеров и состояний;
4. параллельная запись `VkCommandBuffer`.

Предыдущая история: `docs/parallel_gpu.md`. Стадия 4 уже есть (сегменты командных буферов,
`BB_VK_RECORD_THREADS`, отправка из потоков записи). Часть стадии 2 тоже есть: спекулятивная
подготовка draw на `bb:DrawPrep*` (пайплайны, V#/T#/S#, вершинные входы; используется в ~97%
draw). Привязка текстур на отдельном потоке с fork/join на каждый draw выигрыша не дала
(данные гоняются между ядрами).

## Как мерить

Упор в CPU: `~/.claude/jobs/9cdc30a2/tmp/run_cpu.sh` — путь к Лоуренсу, вывод 860×360,
FSR 3.1 Ultra Performance (сцена 286×120), без лимита FPS, Mailbox. Слабый CPU (как Steam
Deck, 4 ядра / 8 потоков): `taskset -c 0-3,8-11`. Профиль стадий: `BB_SECTIONS=1`.
Разброс между прогонами около ±10 FPS: один прогон ничего не доказывает, нужно 3+ чередующихся.

При обычных настройках пользователя (2560×1080, FSR 4.1.1 Native AA, RX 7800 XT) упор в GPU:
154 FPS, stage B занят 55%, stage A ~30% времени ждёт GPU. Там переделка конвейера FPS
не прибавит.

## Этап 1: воркеры разрешения констант (сделано, `BB_RESOLVE_WORKERS=n`, по умолчанию 0)

Stage A больше не проверяет и не копирует маленькие read-only буферы: он резервирует в пакете
`RingBinding` с `RingPending` и отмечает байты в `pending_resolve`. Воркеры `bb:ResolveN`
забирают пакеты по номерам (`DrawPipe::StartResolvers`, таблица слотов), делают проверки
(`IsRegionGpuModified`, `PendingWriteOverlaps`, `LayerMirrored`), копируют в своё кольцо
(`worker_rings`, отметка тиков по-прежнему stage B) или помечают `RingNotCopied` и отмечают
чтение в `pending_reads`. Stage B ждёт флаг готовности пакета. Выгрузка CE
(`WaitForPendingReads`) сначала ждёт `WaitResolved` для пакетов, читающих её байты.
Таблицы `PendingReads` стали атомарными.

| | без воркеров | 1 воркер | 2 воркера |
|---|---|---|---|
| 16 потоков | 300–303 | — | 298 |
| 8 потоков | 228–232 | 230 | 217 |

Stage A: кольцо 2,1 → 0,48 мкс, пакет 4,4 → 3,3 мкс, простой stage A 20–25%. FPS не изменился:
на 16 потоках упор перешёл в stage B (90%), на 8 потоках не хватает ядер.

## Переподписка на 8 потоках

Загрузка потоков (CPU-режим, 8 потоков, по `/proc`): stage B 98%, stage A 84%, главный поток
игры 84%, запись Vulkan 58% + 26%, `bb:DrawPrep` 4 × 22%, `bb:DrawScan` 15%, плюс потоки
игры (GX, Havok, CSChr) ~150%. Почти 7 из 8 ядер; часть наших потоков крутится в ожидании.
На слабом CPU выигрыш даёт меньше лишней работы, а не больше параллельных стадий.

Ручки: `BB_PREP_WORKERS` (по умолчанию половина потоков), `BB_VK_RECORD_THREADS`
(2 при 8 потоках), `BB_PIPE_SPIN_US` (50 мкс при < 12 потоках). Одиночные прогоны: 1–2 потока
подготовки и 1 поток записи дают +2…+9%, но в пределах разброса; серия по 3 прогона — ниже.

## Этап 2 (не сделан)

Вынести с stage B поиск буферов, вершин, индексов и текстур (~1,1 мкс на пакет). Препятствие:
`ObtainBuffer`/`LayerBind` не чистый поиск (Maintain, ловушки записи, NoteUse, перенос блоков в
VRAM), а кэш текстур меняет состояние при обновлении изображений. Выносить можно только чистые
поиски с проверкой поколений на stage B. Ожидаемо +10–20% там, где упор в stage B (12+ потоков).

## Серии по 3 прогона (CPU-режим) и новое значение по умолчанию

Потоки спекулятивной подготовки draw (`BB_PREP_WORKERS`):

| | по умолчанию было | лучше |
|---|---|---|
| 8 потоков | 4 потока: 236, 239, 239 (238) | 1 поток: 250, 243, 246 (247, +3,7%) |
| 16 потоков | 8 потоков: 315, 317, 315 (316) | 4 потока: 333, 333, 331 (332, +5,3%) |

`DefaultWorkerCount` теперь: четверть аппаратных потоков от 12 (16 → 4), иначе 1. Проверка новой
сборки: 8 потоков 254 FPS, 16 потоков 333 FPS.

Воркеры констант поверх нового умолчания (по 2 прогона): 16 потоков 326/332 без них против
324/323 с одним; 8 потоков 245/226 против 240/240. Пользы нет, `BB_RESOLVE_WORKERS` остаётся
выключенным. Stage B занят ~87% и ограничивает дальше; без этапа 2 стадии не масштабируются.
