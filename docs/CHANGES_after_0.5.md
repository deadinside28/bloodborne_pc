# Изменения после 0.5 (с 2026-10-10)

Замеры — RX 7800 XT / RADV, сохранение пользователя (Соборный округ), 1080p.

## Все розничные издания получают профиль игры (#119)

- Профиль Bloodborne (`gpu/games/bloodborne.cpp`) выбирался только для CUSA03173. Американское
  издание (CUSA00900) и остальные регионы запускают тот же исполняемый файл 1.09, но шли без
  профиля, и новая модель падала при входе в мир: `Guest fault ... at guest offset 0x2085xxx,
  address (nil)` в аллокаторе игры (#119, RX 7600, US-издание).
- Воспроизведено у себя на CUSA03173 с `BB_GAME_PROFILE=none`: то же падение (`0x208596a`) при
  входе в мир. С профилем, но без перехватов (`BB_GUEST_HOOKS=0`) — не падает: спасает
  `DynamicWriters` — код аллокатора, чьи служебные данные лежат в памяти GPU; без этой отметки
  их блоки уходят в VRAM-копию.
- Профиль, проверка игры (`scripts/game_check.py`), патчи (`scripts/patches.py`), «звуковой
  фикс» сохранений и папки модов теперь знают все издания: CUSA00900, CUSA00207, CUSA00208,
  CUSA00299, CUSA01363 и издания с The Old Hunters CUSA03179, CUSA03173, CUSA03014, CUSA03023.
- Проверка игры: другие регионы базовой игры без обновления просят 1.09 вместо «поддерживается
  только CUSA03173»; eboot.bin со вшитым патчем 60 FPS (падает в меню жестов) — отдельное
  сообщение (PR #117).
- Осталось: общий путь без профиля должен не падать сам (служебные данные аллокатора в
  VRAM-копии). Сейчас он нужен только для чужих игр.

## Размытие в движении на весь кадр в новой модели (#122)

- С включённым размытием в движении (по умолчанию) кадр при повороте камеры размазывался целиком,
  в старой модели — нет (#122, RX 9060 XT). Воспроизведено: резкость кадра во время поворота
  (стандартное отклонение лапласиана) 6,9 против 8,5–12 в старой модели.
- Поиск: `BB_GARLIC_VRAM_RANGE=начало,конец` (новый диагностический ключ: VRAM-копии только в
  этом диапазоне) и деление диапазона пополам — блок 64 КиБ `0x104ff00000`. Его читает только
  видеочип (буфер 11,4 МиБ каждый кадр), записей буферами и процессором нет: это память
  рендер-таргета, который игра потом читает как буфер.
- Причина: выгрузка изображения в память игры шла через staging и отложенную запись процессора,
  когда у этой памяти была VRAM-копия; копия обновлялась лишь после той записи (инвалидацией) —
  буфер читал данные прошлых кадров. Теперь видеочип копирует изображение и в арену (VRAM-копию)
  в порядке потока; в память игры — как раньше. И `IsRegionGpuModified` считает изменённым то,
  что видеочип записал в VRAM-копию (`gpu_written_bytes`, не на месте): без этого обновление после
  записи процессора поверх затирало копию старыми байтами (`BB_GPU_DATA_CHECK=0` — как раньше).
  Нужны обе правки. После: 11,9–13,0, как в старой модели; FPS тот же (127–131 в обоих
  вариантах, по три запуска).

## Нехватка VRAM на 4 ГБ больше не останавливает игру

- RTX 3050 4 ГБ, старая модель (Авто на NVIDIA), 0.5: три падения за вечер —
  `Failed to allocate 64 MiB for guest memory copies: ErrorOutOfDeviceMemory`. Запасного типа
  памяти (системной) для арены нет: разреженные буферы NVIDIA берут только VRAM. В pre5
  сборщик текстур стал держать текстуры по 5 с (FPS не падал со временем), и на 4 ГБ VRAM
  заканчивалась.
- Теперь: блок поменьше (ровно запрошенный), затем любой другой тип памяти, к которому можно
  привязать арену; и 30 с сборщик под давлением снова выселяет по отправкам, как до 0.5. Он же
  делает так сам, когда занято больше 92 % бюджета драйвера (`VK_EXT_memory_budget`, раз в
  секунду). Проверить можно только на такой карте.

## Выход из игры с геймпада (#74, #116)

## Мышь

- Камера мышью: щелчок в окне игры захватывает мышь (относительный режим SDL), F1 или уход из
  окна — отпускает; меню настроек и ввод имени тоже отпускают. Движение мыши — правый стик:
  отклонение по скорости мыши (~1000 пикселей/с — полный поворот при чувствительности 1), за
  60 мс спадает; движущаяся мышь сразу проходит мёртвую зону игры (`BB_MOUSE_DEADZONE`, 16 из
  127), так что медленное прицеливание тоже поворачивает камеру. Одинаково при любом FPS.
- Кнопки мыши и колесо — те же «клавиши» в привязках: `Mouse Left` R1, `Mouse Right` L2 (огнестрел),
  `Mouse Middle` R3 (захват цели), `Mouse X1` R2, `Mouse X2` L1, колесо — крестовина вверх/вниз
  (быстрые предметы); каждое деление колеса — короткое нажатие. Кнопки работают только при
  захваченной мыши: щелчок, который её захватывает, не атакует.
- bbport.ini: `mouse_look=0/1`, `mouse_sensitivity` (0.05–20), `mouse_invert_y`; лаунчер —
  *Управление*: «Камера мышью», чувствительность, инверсия; «Клавиатура и мышь» — назначение
  кнопок, «Назначить» принимает и кнопку мыши/колесо. Основа — PR #108 (виртуальный стик от
  движения мыши); раскладка клавиатуры не менялась.

## DLSS в AppImage и своя библиотека NVIDIA

- Сборка с `DLSS_SDK_ROOT` (DLSS SDK 310.9.1 с github.com/NVIDIA/DLSS) кладёт в пакет мост
  `libbbport_dlss.so`, `libnvidia-ngx-dlss.so.310.9.1` и `NVIDIA-DLSS-LICENSE.txt` (лицензия RTX
  SDK разрешает распространение в составе приложения, не отдельно). Тестовый AppImage:
  `dist/…-test-1010-dlss.AppImage`.
- Лаунчер, *Апскейлер → DLSS: библиотека NVIDIA → Выбрать файл…* — как DLL для FSR 4.1.1:
  `libnvidia-ngx-dlss.so.<версия>` копируется в `<user>/dlss/`, игра берёт её раньше встроенной
  (лог: `DLSS: NVIDIA's library from …`). Выбранная `nvngx_dlss.dll` — подсказка, что нужна
  библиотека для Linux. Мост ищется рядом с `bb-probe`, затем в `<user>/dlss/`.
- Мост собирается и с защитными флагами Nix (`-Werror=format-security`).
- Проверено на RX 7800 XT только до «not an NVIDIA GPU»: путь к библиотеке (встроенной и
  своей) выбирается верно. Сам DLSS — на карте NVIDIA RTX.

## Онлайн (shadNet) — отдельным модулем

- `gpu/bbnet` → `out/gpu/libbbnet.so`: сетевые и PSN-библиотеки shadPS4 из shadp2p (форк shadPS4,
  GPL-2.0) с клиентом shadNet, перенесены из Linux-форка bbport с онлайном (а тот — из Windows-порта).
  Модуль собирается отдельной целью, его C++ скрыт (`-fvisibility=hidden`, `-Bsymbolic`), наружу —
  только `bbnet_init` и `bbnet_resolve` (`gpu/bbnet/bbnet.h`). Свои заголовки модуля
  (`gpu/bbnet/include`) только дополняют общие: в `gpu/shim` и `gpu/shadps4` ничего не менялось.
- Рантайм (`src/runtime_net.c`): с `BB_ONLINE=1` на первом сетевом/PSN-импорте загружает модуль
  (`dlopen`, `RTLD_LOCAL`; `BB_NET_MODULE` — другой путь), отдаёт ему данные игры и гостевые потоки
  для обратных вызовов NP; трофеи, голос и диалоги магазина остаются в рантайме. Без `BB_ONLINE`
  модуль не загружается; без модуля или если он не стартовал — офлайн, как раньше.
- Сборка: protobuf, nlohmann_json, OpenSSL, zlib, miniupnpc (`shell.nix`); без них модуль не
  собирается (`BB_NET=OFF` — вручную), порт собирается как раньше. AppImage содержит модуль.
- `run.sh`: перенаправления адресов (`scripts/online.py`: сервер игры → The Hunter's Dream,
  знаки призыва → WebAPI shadNet), сервер shadNet по умолчанию `srv.shadps4.net:31313`.
- Лаунчер: страница *Онлайн* (сервер игры, сервер кооператива и WebAPI, учётная запись shadNet,
  UPnP, проверка соединения); `settings.json` — только для владельца (0600, там пароль).
- UPnP: порт P2P теперь открывается на роутере, когда транспорт готов, и закрывается при выходе
  (#121: `AddMapping` не вызывался нигде).
- Проверено: `tests/test_online.c` (импорты сети и NP → модуль, трофеи → рантайм); игра с
  `BB_ONLINE=1` без учётной записи доходит до уровня (модуль: 1399 функций; «no users connected
  to shadNet»). Вход в shadNet и призыв не проверены: нет учётной записи, а UDP-часть публичного
  сервера, по #121, не отвечает.
- HTTPS в AppImage: «Не удалось получить информацию от сервера Bloodborne» — проверка сертификата
  The Hunter's Dream проваливалась (`SSL server verification failed`): OpenSSL из Nix берёт корневые
  сертификаты из `/etc/ssl/certs/ca-certificates.crt`, а на NixOS это ссылка в `/nix/store` хоста,
  которого внутри AppImage не видно. Обёртки пакета теперь задают `SSL_CERT_FILE` на свой пакет
  сертификатов (`nss-cacert`), если указанный не читается; `run.sh` из исходников берёт системный.
  Лаунчер: текст ошибки в проверке соединения не терялся из-за разметки (`<urlopen error …>`), значки
  — из темы Adwaita.

## Мерцание главного меню при выводе выше 1080p

- С живой сменой разрешения (вывод 3840×2160 на мониторе 2560×1080) главное меню мерцало: часть
  кадров показывалась в родных 1920×1080 игры, остальные — с интерфейсом в разрешении вывода
  (4 из 50 снимков). `BB_UI_TRACE=1` (новая диагностика: отрисовки кадров без интерфейса в
  разрешении вывода) показал: пока меню анимирует подсветку, игра рисует его другими шейдерами
  Scaleform (`bb4d5f8c`, `e94b5b06`, `9951d199`, `44072322`, `a334a845`), а не `09957251`; их не было в
  списке шейдеров интерфейса (`ui_composition.h`), и такие кадры не собирались в разрешении
  вывода. После: 0 из 80; в уровне картинка та же.

## AppImage меньше

- В пакете были весь Mesa с LLVM (~800 МБ: нужны только Vulkan-драйверы RADV и ANV), полный GCC
  и заголовки Vulkan (их пути в отладочной информации `bb-probe`), 32-битная половина MangoHud
  (вторые glibc, gtk3, icu, perl) и GStreamer у GTK4 лаунчера. Теперь: свои RADV (без LLVM, ACO)
  и ANV без остального Mesa, `bb-probe` без отладочной информации, MangoHud 64-битный, GTK4 без
  GStreamer, печати и tracker.
- Ещё: SDL3 без зашитого zenity (тот тянул вторую GTK4 с GStreamer; теперь zenity хоста, если
  есть), libdecor без плагина GTK 3 (у SDL3 и у glfw MangoHud; рамки рисует его cairo-плагин),
  MangoHud без xdg-utils (Perl; `xdg-open` хоста). Сборка своей Mesa включает Dozen только потому,
  что рецепт nixpkgs ждёт его выход `spirv2dxil`; в пакет он не попадает.
- Итог: AppImage 925 → 399 МБ, пакет без сжатия 2,85 → 1,06 ГБ. Проверено: лаунчер открывается,
  игра из пакета стартует на встроенном RADV до титульного экрана.

# После 0.51: уход от эмуляции

## Occlusion-запросы игры — по умолчанию настоящие (новая модель)

- Были выключены (заглушка «всё видно»): с апскейлером свечение лампы однажды вспыхивало серым.
  Найдено: проход, нарисованный в другом размере, чем цель игры (уменьшенная сцена; интерфейс в
  разрешении вывода), считал пиксели в своём размере — игра получала 1/4 или 1/9 счёта PS4 (лампа
  в часовне Одеона: 84 286 при 960×540 и 37 455 при 640×360 вместо 337 280 при 1920×1080).
- Теперь у каждого отрезка запроса — коэффициент его прохода (`target_scale` растеризатора,
  8.8 в фиксированной точке), шейдер сложения (`occlusion_resolve.comp`) умножает на него: при
  пресетах 0, 3, 4 игра читает одинаково — 337 249 / 337 149 / 337 122 и 43 814 / 43 761 / 43 750.
- Вспышки не воспроизвелись: 8 направлений с неподвижной камерой по 25 кадров (разброс яркости
  ≤ 1 %, лампа в кадре в 6 из 8) и поворот камеры (80 кадров) при 640×360, вывод 3840×2160 с
  FSR 4.1.1. FPS тот же (100–104 против 99–101 с заглушкой). Самотест PM4 — 11 из 11.
  `BB_OCCLUSION_QUERIES=0` — заглушка. `BB_OCCLUSION_SAMPLES=N` — диагностика: сколько пикселей
  прочла игра.

## Модуль памяти слоя — по умолчанию на всех видеокартах (новая модель)

- На AMD новая модель держала память игры в sparse-арене, на остальных — в модуле памяти слоя (без
  sparse-привязки). Теперь модуль и на AMD: на RX 7800 XT он быстрее арены — маршрут по Ярнаму
  4,30 против 4,60 мс на кадр (p99 5,8–6,0 против 6,6), Сон охотника с поворотом камеры 4,8–5,0
  против 5,2–5,3 мс, часовня Одеона 234 против 213 FPS.
- И только с ним игра верна без профиля игры: с ареной в такой игре (так шло американское издание
  до 0.51, #119) чтение 512 КБ окна из устаревшей VRAM-копии затирало учёт аллокатора, записанный
  процессором, — падение на входе в мир (гость `0x208596a`). С модулем без профиля — 196 FPS, без
  падения.
- `BB_LAYER_MEMORY=0` — sparse-арена (только AMD), как раньше.

## Нагрузка потоков: где упор (новая модель, RX 7800 XT, Ryzen 7 5700X3D)

Сон охотника (горящий), стоя, ~860 draw за кадр, FSR 4.1.1, пресет 3 (сцена 960×540 → 1080p).

- **Упор — видеокарта**: занята ~97 % (sysfs). Из 5,05 мс кадра FSR 4.1.1 — 1,09 мс, шейдер
  копирования игры — 0,31 мс (58 dispatch), полноразмерные копии сцены для игры — 0,22 мс,
  промежутки между отправками — 0,6 мс.
- Процессор: поток записи draw (`bb:DrawRec`, стадия B) — 92–95 % ядра, из них 12–15 % —
  ожидание пакетов; декодер PM4 (`GpuComm`) — 66 %; главный поток игры — 53 %, её `GXRenderThread`
  — 27–30 %. Игра ждёт предыдущий кадр 2,7–2,9 мс на кадр: запас у неё есть.
- С лёгкой нагрузкой на GPU (FSR 3, пресет 4) потолок процессора — ~225 FPS: тогда упор —
  стадия B (занята ~90 %), один поток. На процессорах слабее упор в неё наступает раньше.
- Игра отправляет ~62 командных буфера за кадр, тремя пачками. Глубина перекрытия кадров
  (`BB_SUBMIT_AHEAD` 2–6) FPS не меняет. Интервал отправок (`BB_HONEST_FLUSH_US`) 500–1000 мкс —
  +0,5 %, в пределах разброса, ценой +5 % процессора на потоках записи Vulkan; 4000–8000 —
  хуже (188–196 FPS). Оставлено как было.
- Статистика (`BB_FRAME_STATS=1`) стоит ~2 % FPS: её таймеры стоят в пути каждой привязки.

**Ускорено — стадия B, привязки буферов через модуль памяти** (было 17 % её времени, стало 12 %):

- Очередь переноса блоков в VRAM (`LayerQueuePromotion`) запоминала диапазоны в 256 ячейках по
  первому блоку: диапазоны из одного блока (потоки вершин одного буфера) вытесняли друг друга,
  каждый восьмой вызов заново обходил ~18 блоков под блокировкой модуля. Теперь — хеш по всему
  диапазону (4096 ячеек) и ещё память по блокам (данные, которые игра пишет в кольца, каждый
  кадр по новым адресам); раз в секунду всё смотрится заново. 4,2 % → 0,6 % времени стадии B.
- `LayerInPlace` (буфер куска памяти игры и смещение) запоминается до следующего снятия
  отображения игрой: 2,0 % → 1,1 %. Память `Resolve` — тот же хеш, 2048 ячеек.
- Таблицы — в куче: `thread_local`-массивы на сотни килобайт ложатся в статический TLS каждого
  потока, и потоки игры с маленьким стеком не создавались (`pthread_create failed: 22`).
- Итог: работа стадии B −6 % (её время на пакеты 86 → 81 %, ожидание пакетов 8 → 13 %); FPS на
  этой машине не изменился — A/B поочерёдно, с одного замороженного сохранения: FSR 4.1.1
  200,1 → 199,7, FSR 3 пресет 4 226,0 → 225,8 (разброс ±1). Ни один ресурс не упирается в 100 %:
  GPU ~90 %, стадия B ~85 % работы, игра ждёт кадр 2,7 мс; время кадра задаёт цепочка «игра →
  декодер → запись → GPU», а игре можно быть впереди GPU лишь на кадр (её правило с PS4: дальше
  её куча течёт). Запас стадии B пригодится на процессорах слабее. Прогулка 2 минуты, кадры, игра
  без профиля, самотест PM4 (11 из 11) — без ошибок.
- Ещё мелочи стадии B: `GetDrawOffsets` принимал тип описания выборки вершин без `const` — каждый
  draw копировал его со списком атрибутов (malloc); масштаб occlusion-прохода брал мьютекс на
  каждом draw; метка времени записи GPU по огромному диапазону шейдера копирования (~60 раз за
  кадр, по записи на каждый МиБ) — теперь раз за отправку.
- Найдено, но не сделано: между соседними dispatch шейдера копирования игра ставит `ACQUIRE_MEM`
  (сброс кэшей), но не `CS_PARTIAL_FLUSH` — на PS4 они перекрываются, у нас между каждыми двумя
  полный барьер (0,31 мс GPU за кадр на 58 dispatch). Снять его — до ~3 % GPU, но риск гонки в
  данных игры; без проверки глазами не трогал.

Инструменты: `BB_FPS_PRINT=1` — частота кадров раз в 5 с без статистики
(`tools/restart.sh` с `BB_FRAME_STATS=0` включает её сам); в `BB_TIMELINE` — простои стадии B;
в `BB_GPU_PROFILE` — начало каждой отправки (видно, что промежуток между отправками — не
копирования в её начале: 0,006 мс на кадр).

## Камера мышью — нативно, без правого стика

- Было: движение мыши превращалось в отклонение правого стика, а дальше — путь стика в игре: мёртвая
  зона, кривая отклика, разгон и предельная скорость поворота. Мышь ощущалась как стик.
- Найдено (обратная разработка): камера игры (`ChrExFollowCam`, обновление `0x143ac60`, `rdi` —
  камера) каждый кадр выводит углы из положения камеры вокруг персонажа — наклон в `+0x140`
  (ограничен `+0x1f0`…`+0x1ec`), поворот в `+0x144` (в пределах ±π); в обычном режиме
  `0x143cde0`…`0x143cdf0` считает приращение «стик камеры × скорость × время кадра» и прибавляет
  его к углам, по ним камера ставится заново. Путь стика к ней: устройство пада (`+0x1e4`…),
  виртуальные входы 62/66 (X) и 63/67 (Y), действия `0x48`/`0x49`, манипулятор (`+0x40`).
- Теперь: перехват в `0x143cde0` прибавляет к этому приращению поворот мыши с прошлого обновления
  (радианы, забирается атомарно) и отмечает ввод активным, как делает стик (иначе игра сразу
  возвращает наклон к углу покоя). Мышь поворачивает камеру ровно на столько, на сколько
  сдвинулась, без мёртвой зоны, разгона и предела скорости, независимо от FPS; ограничение наклона
  и обход препятствий — игровые. Чувствительность 1 — 0,0015 рад на пиксель (1000 пикселей —
  86°). Где камера поворот не берёт (захват цели, меню, ролики: её обычное обновление не идёт,
  поворот не забран 100 мс), мышь, как раньше, ведёт правый стик — захват цели переключается
  движением мыши. `BB_NATIVE_MOUSE=0` — только стик.
- Клавиатура: в игре (сборка PS4) нет своего устройства клавиатуры — библиотека ввода
  (`DLUserInput*`) знает только пад, а действия игры привязаны к его кнопкам. Клавиши остаются
  назначениями на эти действия, как и было: «нативнее» их подать в игру нечем.
- Проверено: поворот мышью влево/вправо и вверх/вниз (направления — как у стика), минута ходьбы
  с поворотами мышью, без ошибок. Для тестов `BB_PAD_FILE` понимает `mdx=`/`mdy=` (пиксели за
  чтение пада).

## Ультраширокие и другие соотношения сторон — на лету, хуками

- Отдельно **соотношение сторон** (Авто — по монитору, 4:3, 16:10, 16:9, 21:9, 32:9) и
  **разрешение** из списка этого соотношения, от 360–480 строк (4:3: 640×480 … 2880×2160; 16:10:
  640×400 … 3840×2400; 16:9: 640×360, 854×480, 960×540, 1280×720 … 3840×2160; 21:9: 860×360,
  1280×540, 1720×720, 2560×1080, 3440×1440, 3840×1600, 5120×2160; 32:9: 1280×360 … 7680×2160;
  «Авто» добавляет размер самого монитора). Смена соотношения сохраняет высоту. Меняются на лету
  (`live_resolution=1`; при патче разрешения на старте — после перезапуска). В bbport.ini:
  `aspect_ratio=auto|4:3|16:10|16:9|21:9|32:9`, `output_res=WxH`. Меню игры, оверлей и лаунчер.
- Кадр игры остаётся 1920×1080 — код игры не патчится. Вместо этого:
  - камера (хуки на 5 копированиях параметров проекции в менеджере камеры, `0x1436c2c` …):
    соотношение сторон вывода; шире — больше видно по бокам (вертикальный угол прежний), выше
    (16:10) — угол по вертикали расширяется (`2·atan(tan(fov/2)·(16/9)/A)`, x87 в заглушке),
    ширина обзора прежняя;
  - сцена рисуется в прокси-целях с соотношением вывода (масштаб по осям разный, `FragCoord`
    пересчитывается по осям), апскейлер выдаёт кадр вывода;
  - интерфейс (Scaleform): игра каждый кадр задаёт вьюпорт каждому фильму (`0x1f59100` →
    `MovieImpl::SetViewport` `0x1f510`, режим ShowAll); хук подставляет пиксельное соотношение
    сторон вывода (`Viewport::AspectRatio` = (ширина/высота)/(16/9)) — фильм сам показывает свой
    экран 16:9 посередине более широкой (высокой) видимой области, сжатой в кадр 1920×1080, а вывод
    растягивает её обратно; то, что за краями экрана игры, рисуется, а не отбрасывается;
  - HUD прижат к краям вывода и следует за сменой соотношения: группы `fe.gfx` двигаются так же,
    как игра двигает свои клипы — `SetMember("x"/"y")` объектов Scaleform (ObjectInterface игры:
    GetMember `+0x28`, SetMember `+0x30`) в ежекадровом обновлении игрового экрана (`0x1bf9e10`;
    HUD — `экран+0xa80`, значения берутся и отпускаются в том же кадре: фильм HUD выгружается с
    областями): полосы, предметы, эффекты — к левому краю, отголоски крови, озарение и значок
    автосохранения — к правому; на 4:3/16:10 верхние — вверх, полоса босса — вниз
    (`BB_HUD_ANCHOR=0` — в середине 16:9);
  - полноэкранные заливки и подложки интерфейса (затемнение меню — игра рисует его чуть больше
    своего экрана, — «Вы погибли», затухания) растягиваются на весь вывод: вершинный шейдер
    переносит в углы вывода вершины, лежащие в углах экрана игры или за ними (сразу по x и по
    y); то, что HUD вынес за край только по одной оси, маски Scaleform и всё под ними (тест
    трафарета: например, лента иконок предметов, скользящая в слоте) остаются на месте
    (`motion_param` этих отрисовок; кэш шейдеров пересобирается один раз: версия 18); большие
    картинки (титульная, 2048×1024) и текст — без растяжения; `BB_UI_DRAWS=<файл>` — отрисовки
    интерфейса одного кадра в лог;
  - кадры без сцены (титульный экран, загрузки): поля за экраном игры чёрные (фильмы заливают
    свою расширенную область цветом фона, серым у титульного);
  - метки над персонажами (захват цели, полосы здоровья врагов, урон): хуки на трёх местах их
    перевода в координаты интерфейса (`0x1644379`, `0x1644c45`, `0x16452b7`) умножают на вектор
    порта — метка встаёт над своим персонажем; за краями области 16:9 их скрывает сама игра.
- Меню игры: страница «Изображение» — соотношение сторон, разрешение, апскейлер, пресет, резкость,
  детализация; выбор — строкой игры со всплывающим списком (та же, что у её языковых настроек,
  `0x1b29370`) вместо полосок 0–10. Сквозь список были видны строки ниже (в макете
  ControllSetting строки сложены «вверх»): рантайм отдаёт игре копию `menu/optionsetting.gfx`, где
  у этого макета глубины строк развёрнуты, как у её LanguageSetting (меняются только поля глубины;
  файл на диске не трогается; `BB_GAME_MENU=0` — как есть). После смены соотношения строка
  «Разрешение» сразу показывает размер в новом соотношении (та же высота), а её список — ровно
  размеры этого соотношения: строка игры держит свои значения (`строка+0x3d8`, по 0x48 байт, число
  `+0xce0`), их тексты берутся из буферов порта при показе; хук ввода строк страницы (`0x1b26b00`,
  поток меню игры) переписывает значения и число, и строка показывает их заново (`0x1b2b7c0` —
  текст значения, `0x1ad06e0` — тексты списка). Счётчик FPS — в оверлее и лаунчере.
- Также: «Авто» знает монитор окна (и его смену); FSR 4 после неудачи на неподдерживаемом выводе
  (7680×2160 без ассетов 4320) снова пробуется при смене вывода, а не остаётся на FSR 3.1.
- Ограничения: FSR 4.1.1 — вывод до 3840×2160 (5120×2160, 5120×1440, 7680×2160 — FSR 3.1);
  метки над персонажами за краем области 16:9 скрывает сама игра (её проверка границ экрана).
- Убрано: прежний вариант через патч кода при загрузке (`bloodborne_display.cpp`, `BB_GAME_FRAME`,
  кадр игры шире 1920×1080).

## NVIDIA: 0.51 не запускалась (CreateDevice: ErrorInitializationFailed) (#135, #147, #152)

- С DLSS (библиотека NVIDIA рядом) устройство Vulkan создаётся с расширениями NGX; драйвер их
  объявляет, но для них грузит `libcuda.so.1` (и нужен модуль `nvidia-uvm`). Лаунчер AppImage
  выкладывал в свою папку библиотек NVIDIA только `libnvidia-*`, `libGLX_nvidia`,
  `libEGL_nvidia` — `libcuda` не находилась, `vkCreateDevice` давал ErrorInitializationFailed, а
  игра шла дальше и падала на «Invalid device» (код 134/-1); в т. ч. на картах без DLSS (GTX
  1660), раз библиотека DLSS лежит в AppImage.
- Теперь: лаунчер кладёт туда и `libcuda.so*` (`launcher/bbport_vulkan.py`); если устройство с
  расширениями NGX всё же не создаётся — второе создание без них, DLSS выключен (в журнале
  причина), игра на FSR 3.1, выбор DLSS в настройках остаётся; без устройства вообще — понятная
  остановка, а не падение дальше. (Те же исправления предлагали PR #137 и #140.)

## Новая модель: буферы размером с кадр снова в VRAM (#149)

- RX 7900 XT, вывод 3840×2160 с патчем разрешения на старте (сцена 2560×1440): 0.4 — 136 FPS,
  0.51 — 58 (старая модель — 128). Здесь (RX 7800 XT, та же конфигурация): новая модель 95 FPS,
  старая 130; GPU 10.5 мс на кадр против 7.85. Попиксельный проход (`cs 3d5ebf4e`, 58880 групп)
  писал буфер размером с кадр (19.9 МБ) в память игры через шину, 1.8 ГБ/с, и соседние проходы
  его там же читали.
- Причина — модуль памяти слоя (с 0.5 по умолчанию): привязка, которую GPU пишет, должна целиком
  лежать в одном зеркале VRAM, иначе весь её диапазон уходит в память игры, а со второго раза —
  навсегда (`dynamic_blocks`). У этого буфера 303 блока из 305 были в зеркале; первый и последний
  блок он покрывает лишь частично (начало не выровнено на 64 КБ), остальные их байты модуль не
  знает (ни загрузчик, ни GPU их не писал) — в зеркало их не брали. С разрешением 1080p буферы
  так не ложились.
- Теперь такие крайние блоки записываемой привязки идут в зеркало с ней (если процессорную запись
  туда ловит ловушка — `layer_edge_blocks`): процессор, записав рядом, отправляет блок на место, и
  байты GPU в нём сначала копируются обратно (только записанные GPU диапазоны). Здесь: 95 → 132
  FPS (старая модель — 130); живая смена разрешения и обычная конфигурация — без изменений
  (120 и ~194 FPS); кадры те же. Диагностика: `BB_RESIDENCY_MIX=2` (привязки «на месте» с
  наибольшим объёмом и почему).

## Старая модель памяти: VRAM больше не копится до падения (#142, 4 ГБ)

- Старая модель (по умолчанию на NVIDIA) держала в VRAM каждую копию памяти игры, которую хоть
  раз копировала: область за областью «guest blocks in VRAM» росли (1.6 ГБ на 4-гиговой карте) и
  через час-два «Failed to allocate .. MiB for guest memory copies: VRAM is full» останавливал
  игру (у NVIDIA разреженная арена берёт только VRAM).
- Теперь: на картах до 8 ГБ копии, которые GPU не использовал минуту и в которых нет записанного
  им, уходят из VRAM (при следующем использовании загружаются снова), их места занимают новые;
  при нехватке VRAM — после 5 с, на любой карте; если память на новый блок всё же не выделилась —
  сначала уходят копии, не использованные секунду, и новые блоки встают на их места; опустевшие
  куски возвращаются драйверу. (`BB_VRAM_IDLE_SECONDS=N` — своё время и на любой карте;
  `BB_ARENA_VRAM_ONLY=1` с `BB_RESIDENCY_VRAM_LIMIT_MB` — проверка, как на такой карте.)
- Если рабочему набору области не хватает VRAM целиком, игра по-прежнему остановится — но
  накопления за часы больше нет.

## Частота кадров — хуками, без патчей; привязанное к кадру — по времени кадра

- Выше 30 FPS («Без ограничения», 60, 90) частоту кадров ведут хуки в коде игры
  (`gpu/shim/bbport_frame_rate.cpp`), а не патчи сообщества Uncap FPS++ / 60 FPS++ / 90 FPS++ и
  Sprint Fix (`BB_FRAME_HOOKS=0` — снова патчи, для сравнения). Ставятся при загрузке образа, до
  запуска игры; каждое место сверяется побайтно.
  - Главный цикл (`0x2018d20`): пауза кадра (`0x2034770`) ждёт кадра 1/30 с и измеряет кадр в
    `+0x264`, затем игра шагает на фиксированные 1/30 с (`0x2018e36`). Хуки держат режим паузы
    на одном vblank с целью кадра 1/240 (60/90 и `BB_FPS_LIMIT` — их кадр: ограничивает сама
    игра, до симуляции кадра, а не задержкой готовых кадров), а шаг — измеренное время кадра
    (1/240…1/30 с; ниже 30 FPS игра замедляется, как всегда). Частота смены кадров, которую
    просит игра (`sceVideoOutSetFlipRate`, каждый второй vblank), не действует.
  - То, что игра привязывает к кадру 30 FPS, читает значение текущего кадра: инструкции берут
    константу со страницы рядом с образом (меняется только адрес операнда), значение
    пересчитывается каждый кадр. Шаг 1/30 с → время кадра; доля f за кадр → `1−(1−f)^n`,
    затухание k за кадр → `k^n`, приращение за кадр → `·n` (n — длина кадра в кадрах 30 FPS).
    Всего 48 мест и 2 фиксированных шага подсистем (`0x17f9b71`, `0x1572a7d`): «один кадр» в
    эффектах и таймерах, шаги подсистем (в т. ч. шаг, который игра в своём режиме 60 Гц делает
    1/60), сглаживание камеры (1/30 и 0.1 за кадр), гашение движения персонажа (0.95 за кадр),
    рампа ±0.1 за кадр (`0x19084b0`; в Uncap FPS++ её не было), жёсткость ткани (1.0 при 30 FPS,
    0.5 от 60 FPS — как у патчей 60 FPS).
  - Найдено заново (не было ни в одном патче): таймеры частей тела, которые двигает физика
    (`0x1515ec0` → `0x180df90`, `0x1811650`, каждая часть каждый кадр) шли на 1/30 с за кадр — на
    200 FPS в 6–7 раз быстрее; и гашение «упора в стену» у бега (×0.8 за кадр).
  - Бег: проверка «упора в стену» (`0x1514c24`) сравнивала расстояние за кадр ×30 — делится на
    время кадра (скорость при любой частоте; иначе выше ~90 FPS бег падал до шага).
  - Перевод длительностей из кадров 30 FPS в секунды (затухания эффектов, звука, анимаций)
    остаётся 1/30: то, что их отсчитывает, идёт по реальному времени (патчи укорачивали их в
    2–8 раз). Остальные места с 1/30 в коде (67 непосредственных значений, ~100 функций с 1/30,
    30, 1/60, 60) проверены по частоте вызовов (`BB_RE_ENTRY=адреса` — сколько раз и с каким
    xmm0 вызывается функция) — в игре каждый кадр их не зовут, либо это пересчёт единиц.
- Проверка: из одного сохранения 2 с шага и 3 с бега — при 30 FPS, 60 и ~200 FPS персонаж в
  одних и тех же местах.
- Интерфейс (Scaleform) продвигается каждый кадр на реальное время (`MovieImpl::Advance`
  `0x20f00`, `BB_RE_ADVANCE=1`), но его ролики сделаны на 30 кадров в секунду (все 102 в
  `menu/`): анимации их шкал шагают по 1/30 с.

## AppImage: `--play` снова запускает игру

- `Bloodborne-bbport-x86_64.AppImage --play` (игровой режим Steam Deck, ярлыки) падал сразу:
  «python3: Software caused connection abort». Среда AppImage держит смонтированный образ, пока

  там ошибки не было. Теперь журнал пишется в дескриптор, который выбирает bash (10 и выше).

  отрисовок, видеочип загружен на 99 %): свежий запуск 76,6 FPS, после 17 минут игры с
  телепортами по лампам — 55,3 (−28 %); выход в меню и повторная загрузка в том же процессе не
  помогали (54,2). Доля загруженных данных игры с копией в VRAM за это время падала с 84 % до 50 %.
- Причина (`BB_RESIDENCY_MIX=2`: самые тяжёлые привязки «на месте» и их блоки): модуль переносит
  читаемый диапазон в VRAM только целиком, и один блок, который видеочип однажды писал «на месте»
  (`dynamic_blocks`), оставлял весь диапазон в памяти игры — 7-мегабайтная привязка читалась по
  шине из-за одного такого блока из 110. Такие пометки не снимались никогда: при загрузке новой
  области её ассеты ложились в память, где прежние буферы видеочипа оставили пометки (164 → 1117 МиБ
  «динамических» блоков за сессию).
- Теперь блок, который загрузчики игры переписали целиком (все его байты — данные процессора),
  снова может получить копию в VRAM; запись видеочипа в нём остаётся «на месте»
  (`layer_cpu_blocks`), чтобы процессор (транслятор читает там код шейдеров и описатели) никогда не
  видел устаревших данных. Часто записываемые процессором блоки остаются «динамическими».
  `BB_LAYER_RELOAD_RESET=0` — как раньше.
- Проверка: 16 минут игры с телепортами — «динамических» 366–771 МиБ без роста (3 ГБ блоков
  возвращено), смешанные чтения ~300 МиБ за 2 с вместо ~8 ГБ; в точке конца после игры 66–72 FPS,
  свежий запуск там же 67–73 (разброс между запусками ~8 %). Копирование в VRAM 16 → 23 МБ/с.
- Отвергнуто: снимать такие пометки по времени (через 30 с без повода). Через минуту транслятор
  прочитал из памяти игры мусор вместо кода шейдера (рекомпилятор остановился на неизвестной
  инструкции): часть пометок защищает данные, которые видеочип пишет, а процессор читает.
- Снятие отображения памяти игрой теперь сбрасывает все пометки целиком снятых блоков
  (`BB_LAYER_UNMAP_RESET=0` — как раньше). Bloodborne во время игры память не снимает — на неё не
  влияет.
- Диагностика: строка `Layer memory: held in place` раз в 10 с — объём «динамических» блоков, с
  проваленным наблюдением, записанных процессором (и сколько записей видеочипа из-за них осталось
  «на месте» за 10 с), возвращённых после перезагрузки и загруженных данных без копии в VRAM.

## Свой код вместо shadPS4 (кроме онлайн-модуля)

- `gpu/shadps4` удалён: командный процессор, описания GCN, транслятор шейдеров, рендер, кэши и
  платформенные библиотеки — свой код (`gpu/VENDOR.txt`, `docs/SHADPS4_EXIT_PLAN.ru.md`).
  Транслятор проверен на корпусе шейдеров игры: SPIR-V побайтно совпадает с прежним.
- Кэш конвейеров и его хранение на диске — `gpu/render/pipeline_cache.*`, `pipeline_store.*`;
  растеризатор разбит на модули `gpu/render/raster_*.cpp`.
- NVIDIA: конвейеры из кэша на диске теряли шейдер отбрасывания по clip distances (его не
  сохраняли): теперь он сохраняется; старые записи кэша читаются как раньше, без пересборки.
- Конвейеры с геометрическим шейдером из кэша на диске получали пустой fetch-шейдер (его
  затирала стадия без него).
- Отрисовка без пиксельного шейдера брала настройки фрагментной стадии от предыдущей отрисовки
  (NVIDIA: наличие шейдера отбрасывания зависело от порядка отрисовок).
- Отладочные метки Vulkan (`BB_VK_MARKERS=1`) больше не читают за концом строки игры.
