# Повреждение сцены при первой загрузке: SSR — 2026-10-17

Пользовательские снимки: `image_2026-10-17_19-34-43.png` (меню сохранений)
и `image_2026-10-17_19-35-22.png` (сцена с цветными блоками).
Пользователь подтвердил, что сбой возникает уже при первой загрузке процесса:
без Bloom — цветные блоки, с Bloom — белый кадр.

## Проверка причины

Диагностика запускалась на отдельных копиях сохранения в Сне Охотника.
Пользовательские настройки и сохранения не менялись. Управление размером,
положением, монитором и полноэкранным режимом окна не отправлялось.
Снимки получены внутренними дампами рендера.

Материалы: `out/dev/corrupt-load-20261017/`; скрипт
`out/dev/diagnose-corrupt-load.py`.

| Случай | Результат |
| --- | --- |
| `baseline-new`: New, live-эффекты, SSR on, Bloom off | Цветные блоки уже на входе FSR |
| `old`: Old, те же SSR/Bloom | Цветные блоки уже на входе FSR |
| `startup-effects`: New, `BB_HOT_EFFECTS=0`, SSR on, Bloom off | Нормальная сцена |
| `live-no-ssr-bloom`: New, live-эффекты, SSR off, Bloom on | Нормальная сцена |
| `fixed-ssr-bloom`: исправление, New, SSR on, Bloom on | Нормальная сцена |
| `appimage-ssr-bloom`: новый AppImage, New, SSR on, Bloom on | Нормальный вход FSR и представленный кадр; закрыт после контрольных дампов |

Во всех случаях использовались FSR 4.1.1, Native AA, вывод 2560×1080,
RX 7800 XT / RADV. Камера между запусками могла отличаться; это проверка
повреждения изображения, не попиксельное сравнение и не замер FPS.

## Дефект

Live-реализация SSR переносила код и константы патча сообщества, намеренно
пропуская `0x22c428d`: `shr esi,1; shr edx,1` заменяются четырёхбайтным NOP.
Это изменение размеров ресурса в конструкторе. Пропуск оставлял половинную
цель при изменённых проходах SSR. Наблюдения не требуют ни смены сохранения,
ни гипотезы об ошибке FSR или только новой модели памяти.

SSR также занимал несколько записей `hot_code`, но обычное применение настроек
помечало общий effect index применённым уже после первой записи. При переключении
оставшиеся записи могли пропускаться. Отказ от частичного live-пути устраняет
этот путь рассогласования для SSR.

## Исправление

- `scripts/patches.py` снова выбирает полный стартовый патч SSR, включая размер.
- Из `hot_code` удалены частичные live-записи SSR.
- Оверлей и встроенное меню показывают необходимость перезапуска для SSR;
  Bloom остаётся live-эффектом.
- Добавлена проверка полного набора десяти записей SSR, включая четыре байта
  по `0x22c428d`, и классификации SSR/Bloom для меню.

131 Python-тест прошёл после завершения линковки. Native settings,
effect-flags и fx-init-clear прошли. Сборка bbgpu и AppImage успешна;
предупреждения ODR в стороннем FSR остаются прежними.

Предыдущий основной AppImage сохранён как
`dist/Bloodborne-bbport-x86_64-before-ssr-fix.AppImage`.
Основной `dist/Bloodborne-bbport-x86_64.AppImage` пересобран с исправлением.
SHA-256: `ed514586521d6452031e8a708f3cc61661b761c7f074ff0391c0a10dc844d6b6`.

Контрольный AppImage загрузил персонажа в лечебнице; его кадр не сравнивается
попиксельно с наружными кадрами исходной сборки. Диагностических процессов
после завершения не осталось.

Состояние портретов в меню сохранений отдельно не исследовалось: снимок
показывает повреждённый портрет одного персонажа, но не доказывает его связь
с текущим рендером сцены. Длительная игра, повторная смена сохранений и NVIDIA
не покрыты этими короткими контрольными запусками.
