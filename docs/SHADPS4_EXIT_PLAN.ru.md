# Уход от shadPS4: где он стоит, что мешает другим играм, порядок замены (2026-10-12)

> **Итог (2026-10-13): `gpu/shadps4` удалён.** Всё, что в нём было, заменено своим кодом:
> командный процессор (`gpu/cp`), описания GCN (`gpu/gcn`), транслятор шейдеров (`gpu/shader`,
> проверен на корпусе шейдеров игры — SPIR-V побайтно совпадает с прежним), рендер
> (`gpu/render`: конвейеры, кэш конвейеров и его хранение на диске, растеризатор в модулях
> `raster_*.cpp`), кэши буферов и текстур, платформенные библиотеки. От shadPS4 остался только
> онлайн-модуль (`gpu/bbnet/shadps4`: сеть и NP), его не трогали. Дальше — оптимизация с
> сохранением асинхронности (раздел 6) и документация по встраиванию апскейлеров.
> Ниже — план в том виде, в каком он писался.

Требования: минимум накладных расходов (на отрисовку на процессоре, на кадр на видеочипе) и
ничего, что знает одну игру, вне её профиля (`gpu/games/`). Общность проверяется на играх с другим
движком, где, например, частицы целиком на асинхронных очередях compute.

Замеры — RX 7800 XT / RADV, Ryzen 7 5700X3D, сохранение пользователя.

## 1. Сколько shadPS4 осталось

Сравнение `gpu/shadps4` с исходным коммитом b4e7ae7: 118 тыс. строк, из них 88,8 тыс. (75 %) —
строки оригинала.

| Часть | Строк | Своего | На горячем пути отрисовки |
|---|---|---|---|
| `shader_recompiler` | 38,6 тыс. | ~2 % | нет (только компиляция конвейеров) |
| `renderer_vulkan` | 29,5 тыс. | 60 % | да: растеризатор, кэш конвейеров, привязки |
| `amdgpu` (командный процессор, регистры, тайлинг) | 8,7 тыс. | 28 % | да: разбор PM4 (`liverpool.cpp`) |
| `buffer_cache` | 7,8 тыс. | 75 % | да: `ObtainBuffer` (своё) |
| `texture_cache` | 4,8 тыс. | 13 % | да: поиск образов по адресу |
| `core/libraries` (gnmdriver, videoout, avplayer) | 11,8 тыс. | ~8 % | раз в кадр / раз в отправку |
| `common` | 10 тыс. | 1 % | утилиты |

Своё вне shadPS4: модуль памяти (`gpu/layer`), декодер PM4 (`gpu/cp`, включается вручную), профили
игр (`gpu/games`), конвейер стадий A/B, потоки записи Vulkan, апскейлеры, вся процессорная часть
(загрузчик, рантайм `src/`).

## 2. Куда уходит кадр сейчас (замер 2026-10-13)

Одна точка (Ярнам, ~885 отрисовок), RX 7800 XT + Ryzen 7 5700X3D.

**Видеочип, настройки пользователя** (вывод 3840×1600, FSR 4.1.1 Native AA): 14,9 мс на кадр,
67 FPS, видеочип занят на 99 % (`BB_GPU_PROFILE=1`):

| Что | мс/кадр | Доля | Чьё |
|---|---|---|---|
| проходы и запуски самой игры | ~7,5 | ~50 % | игра (перевод — рекомпилятор shadPS4) |
| апскейлер FSR 4.1.1 | 4,18 | 28 % | наше |
| прокси сцены (уменьшение/заливка для проходов, ждущих 1920×1080) | 1,51 | 10 % | наше, плата за перевод разрешения |
| видеочип простаивает между отправками (7 отправок за кадр) | 1,44 | 10 % | наше: граница отправки, синхронизация |
| шейдер копирования игры (60 запусков с полным барьером между ними) | 0,35 | 2 % | перевод барьеров |

**Процессор, лёгкая нагрузка на видеочип** (FSR 3 Ultra Performance): 175 FPS, видеочип всё равно
занят на 99 %; стадия B занята на 72 % (`BB_SECTIONS=1`, мкс на пакет):

| Часть стадии B | мкс | Чьё |
|---|---|---|
| всего на пакет | 2,54 | |
| привязка ресурсов (буферы 0,36, текстуры 0,27) | 0,75 | shadPS4 (`BindBuffers`/`BindTextures`) + наши кэши |
| `ObtainBuffer` (в т. ч. модуль памяти 0,39) | 0,50 | наше |
| вершины и индексы | 0,36 | shadPS4 + наше |
| начало прохода | 0,20 | shadPS4 + наше |
| упорядоченные задачи (метки, DMA) | 0,24 | командный процессор |
| запуски compute | 0,20 | shadPS4 |
| динамическое состояние, дескрипторы, передача потокам записи | 0,36 | смешано |

Вывод: на этой машине упор всегда в видеочип; процессорной части shadPS4 хватает с запасом
(потолок стадии B ~240 FPS при таком числе отрисовок). Время, которое можно вернуть, лежит на
шкале видеочипа, и почти всё оно — в нашем коде и в том, как переводятся синхронизация и барьеры.

## 3. Что в коде shadPS4 мешает «быстро» и «для любой игры»

1. **Командный процессор (`liverpool.cpp`).** Корутины, большой `switch`, CE (`DUMP_CONST_RAM`)
   и DMA/`WRITE_DATA` вне памяти «на месте» исполняет процессор при разборе. Очереди compute
   (ASC) — корутины в том же потоке, **каждый их пакет сбрасывает конвейер стадий A/B**
   (`DrainDrawPipe(ReasonCompute)`). Bloodborne ASC не использует (0 отправок за кадр); в
   играх с асинхронным compute это обычный кадр — параллельность записи отрисовок пропадёт, асинхронность compute
   (перекрытие с графикой) тоже.
2. **Привязка ресурсов.** Каждая отрисовка заново ищет буферы и образы по адресам; SRT walker
   (обход таблиц описателей кодом шейдера на процессоре) выполняется воркером и ещё раз на
   стадии B для проверки. Кэши (`texture set memo` 98–99 % попаданий, `render state memo` ~80 %)
   срезают часть, но строятся поверх того же поиска.
3. **Кэш текстур по адресу и хешу.** Образ угадывается по адресу/формату из T#, наложения и
   «цель рендера как текстура» — эвристики `FindImage`. Для другой игры с другими раскладками
   памяти это главный источник артефактов.
4. **Ключ конвейера собирается из регистров на каждой отрисовке** (`RefreshGraphicsKey`);
   динамического состояния мало — много вариантов конвейеров и компиляций.
5. **Модель памяти** (уже своя) несёт три пути: 0.3, sparse-арена, модуль. Сегодня найдено, что у
   модуля «пожизненные» правила (блок, который видеочип однажды писал «на месте», — навсегда вне
   VRAM) копились при загрузке областей и выводили из VRAM целые диапазоны: −26 % FPS за 17 минут
   с телепортами. Исправлено сбросом при полной перезаписи блока загрузчиком; общий урок — у
   каждого состояния блока нужен явный выход по событию, а не «навсегда».

## 4. Что в видеочасти знает только Bloodborne

| Где | Что | Для другой игры |
|---|---|---|
| `gpu/games/bloodborne.cpp` | перехваты загрузчиков, аллокатора, кучи; писатели «каждый кадр»; хеш шейдера копирования | профиль (уже так) |
| `renderer_vulkan/ui_composition.h` | хеши шейдеров Scaleform (интерфейс в разрешении вывода) | в профиль; без профиля — без раздельного UI |
| `vk_camera_motion.cpp` | распознаёт константы сцены Bloodborne (дальняя плоскость 3000, размер) | в профиль; у игр с размытием в движении может быть свой буфер скоростей, который апскейлер может взять напрямую |
| `vk_scene_resolution.cpp` | «сцена» = цели 1920×1080 | параметр профиля |
| `gpu/shim` | частота кадров, соотношение сторон, меню, мышь, значки кнопок (`KG_*`) — хуки по адресам 1.09 | особенности порта конкретной игры |

## 5. Что нужно другим играм, чего нет или что не проверено

- **ASC как настоящие очереди Vulkan**: своя очередь compute на каждую очередь игры, метки и
  `WAIT_REG_MEM` между очередями — timeline-семафоры; разбор очередей без сброса конвейера A/B.
- **GDS** (ordered append, счётчики, GWS): сейчас частично (DMA/EOS в GDS); нужна память GDS как
  буфер видеочипа с атомарными операциями.
- **MSAA/EQAA с FMASK** (декомпрессия FMASK сейчас пропускается), быстрые очистки CMASK, HTILE.
- **Тесселяция и геометрические шейдеры** — в рекомпиляторе shadPS4 частично; Bloodborne их не
  проверяет.
- **Память без перехватов игры**: корректность только на ловушках записи (64 КиБ); у игры, много
  пишущей в память видеочипа с процессора, это поток срабатываний. Модуль должен работать без
  профиля (сейчас проверено: Bloodborne без профиля — 196 FPS).
- **Рантайм** (`src/`) реализует ровно то, что зовёт Bloodborne; для другой игры — больше
  системных библиотек. Это не shadPS4, но без этого вторая игра не запустится.

## 6. Устройство, к которому идём, и правила низких накладных расходов

1. **Стадия B только записывает.** Всё, что можно решить по снимку регистров и описателей, —
   на воркерах стадии A (простаивающие ядра): конвейер, образы, буферы, сэмплеры, готовый блок
   дескрипторов. Стадия B сверяет поколение (ресурсы не менялись) и копирует блок
   (`VK_EXT_descriptor_buffer`) — цель ~1 мкс на пакет вместо 2,5.
2. **Идентичность вместо поиска.** Образы и буферы — в реестре по идентичности описателя
   (адрес, формат, размеры), недействительны по поколению памяти (ловушки записи, записи
   видеочипа), без хеширования данных игры при использовании.
3. **Состояние по изменениям.** Декодер (`gpu/cp`) отдаёт записанные блоки регистров; группы
   состояния (растеризация, смешивание, глубина, цели) пересчитываются только при их записи.
   Больше динамического состояния (`VK_EXT_extended_dynamic_state3`, динамический ввод вершин) —
   меньше конвейеров.
4. **Командный процессор — транслятор, не эмулятор.** Ничего «вместо видеочипа» на процессоре;
   очереди compute — очереди Vulkan; метки — записи видеочипа (уже так).
5. **Профиль игры — единственное место знаний об игре**: адреса кода, хеши шейдеров, раскладки
   констант для векторов движения, размер сцены, UI.

## 6а. Асинхронность: сколько можно вернуть на видеочипе

| Что | Сейчас | Цель | Как |
|---|---|---|---|
| простои между отправками | 1,44 мс | ~0,3 мс | меньше отправок за кадр (7 → 2–3), запись следующей отправки, пока видеочип занят текущей; ожидания меток — на видеочипе (timeline-семафоры), не на процессоре |
| FSR на отдельной очереди compute | 4,18 мс последовательно | скрыть 30–50 % | апскейл кадра N идёт вместе с растеризацией кадра N+1 (тени, G-буфер — упор в растеризацию, вычислительные блоки свободны); нужны две копии целей сцены (прокси — наши образы: +~150 МБ при 3840×1600) |
| прокси сцены | 1,51 мс | ~0,5–1 мс | часть проходов рисовать сразу в размере сцены (пересчёт `FragCoord` уже есть), уменьшения — на очереди compute |
| барьеры из сбросов кэшей игры | полный барьер на `ACQUIRE_MEM` | точные барьеры | переводить, что игра реально просит (`ACQUIRE_MEM` без `CS_PARTIAL_FLUSH` — без ожидания предыдущего запуска): шейдер копирования 0,35 → ~0,1 мс, плюс остальные проходы |
| async compute самой игры (ASC) | корутины в одном потоке + сброс конвейера A/B на каждом пакете | очереди Vulkan | для Bloodborne 0 (не использует), для игр с асинхронным compute — обязательно |

Оценка для настроек пользователя: −3…−5 мс из 14,9 → 85–100 FPS вместо 67 (+25–45 %); реально
ожидать +25–30 %. Самое дешёвое — простои между отправками и точные барьеры, самое дорогое —
FSR на отдельной очереди (двойные цели сцены, синхронизация с интерфейсом).

На процессоре асинхронность — это перенос решения о ресурсах на воркеры стадии A (стадия B только
записывает) и несколько потоков стадии B по проходам. Здесь это даёт только запас (72 % → ~30 %
занятости стадии B); на Steam Deck и слабых процессорах — разницу между упором в процессор и его
отсутствием.

## 7. Порядок замены

| Шаг | Что | Выигрыш | Риск | Проверка |
|---|---|---|---|---|
| 0 | Память: старение модуля (сделано, проверяется); удалить модель 0.3 и арену после логов NVIDIA | меньше ветвлений в `ObtainBuffer`; один путь | средний (NVIDIA) | маршрут, долгая игра с телепортами, логи тестеров |
| 1 | Командный процессор: `gpu/cp` по умолчанию (найти +7 %), обработчики пакетов из `liverpool.cpp`; ASC → очереди Vulkan + timeline-семафоры; GDS | декодер дешевле; асинхронный compute; нужно играм с асинхронным compute | средний | самотест PM4 + новые тесты ASC/GDS; Bloodborne |
| 2 | Привязки: решение на стадии A, descriptor buffers, реестр образов по идентичности | стадия B ~1 мкс на пакет вместо 2,5 (выигрыш на слабых процессорах и высоких FPS) | высокий (наложения образов) | кадры маршрута 1:1, `BB_SECTIONS` |
| 3 | Состояние по изменениям + динамическое состояние | меньше конвейеров, дешевле ключ | средний | число конвейеров, компиляции в первой сессии |
| 4 | Профили: UI, камера, размер сцены, значки — в `gpu/games` | вторая игра без правок ядра | низкий | Bloodborne без изменений |
| 5 | Платформа: gnmdriver/videoout/avplayer — своё, рядом с рантаймом | меньше кода shadPS4, API PS4 под контролем | низкий | Bloodborne; затем вторая игра |
| 6 | Рекомпилятор шейдеров: оставить (исправления из upstream переносятся), менять точечно (меньше специализаций по описателям) | — | высокий при замене | — |

Рекомпилятор на отрисовку ничего не стоит, а его замена — самый большой риск для картинки.
Уходить от него стоит последним и только если понадобится (например, описатели на видеочипе).
Остальное заменяется за интерфейсами по одному модулю, как в
[TRANSLATOR_ARCHITECTURE.ru.md](TRANSLATOR_ARCHITECTURE.ru.md): сначала интерфейс с кодом
shadPS4 за ним, потом своя реализация, после каждого шага — маршрут, самотест PM4, кадры.

## 8. Чем мерить

`Frame stats` (мкс на отрисовку стадии B, простой), `BB_SECTIONS=1` (разбивка стадии B),
`Draw pipe` (готовые отрисовки, сбросы конвейера по причинам), FPS с лёгкой нагрузкой на видеочип
(FSR 3, пресет 4: упор в процессор), p99 времени кадра, время видеочипа (`BB_GPU_PROFILE=1`),
доля данных в VRAM (`Layer memory: held in place`) на долгой игре.
