# NVIDIA / hybrid laptop: разбор присланных логов 2026-10-17

Это отдельное расследование от PM4/23 при загрузке сохранения и allocation error 9
в катсцене Лоуренса. Изменений в рендерере по этим отчётам пока не внесено:
причины нулевого вызова и остановки загрузки требуют разных проверок.

## EGL и упаковка

В `bbport-vulkan-info (copy 1).txt` задан только
`__EGL_VENDOR_LIBRARY_FILENAMES=/usr/share/glvnd/egl_vendor.d/50_mesa.json`.
Загрузчик открыл NVIDIA ICD, но не получил `vkCreateInstance` через
`vk_icdGetInstanceProcAddr`, после чего остаётся Intel. В другом отчёте с обоими
vendor JSON NVIDIA уже доступна, но возникает другой сбой. Поэтому подстановка
NVIDIA JSON объясняет смену поведения, но не является проверенным исправлением падения.

`launcher/bbport_vulkan.py` сохраняет явно заданный пользователем EGL список;
если он отсутствует, добавляет host vendor JSON. Отдельно выставляет NVIDIA ICD
и каталог ссылок на host NVIDIA libraries перед bundled glvnd/X11/Xext.
В GDB действительно видны host NVIDIA и bundled glvnd, Wayland, GBM, libc.
Такое сочетание требует проверки зависимостей, но само по себе не доказывает несовместимость.

Диагностика перечисляет EGL Wayland/GBM/X11 библиотеки как `not loaded`, хотя
ссылки на них есть. Сейчас это означает отсутствие `calling init` в LD_DEBUG trace,
а не доказанное отсутствие файла. Возможны отсутствующая транзитивная зависимость,
ошибка загрузки или прекращение процесса до инициализации. Полный linker trace
нужен для различения. Автор уже проверил скрытие external platforms без успеха;
считать эти библиотеки единственной причиной нельзя.

Описание NVIDIA EGL external platforms: https://github.com/NVIDIA/eglexternalplatform
и https://github.com/NVIDIA/egl-wayland2 .

## Почему нет core от bb-probe

`src/probe.c` устанавливает обработчик SIGSEGV, который печатает Fault и вызывает
`_exit(128 + sig)`. Это обычное завершение с кодом 139 после перехвата сигнала,
а не обязательное создание core. `No coredumps found` ожидаемо для такого пути.
У отдельного vulkaninfo этого обработчика нет; присланный core относится к нему.
GDB может остановить bb-probe на SIGSEGV до передачи сигнала обработчику.

## Следующие точечные проверки на машине автора

1. Для зависания получить встроенный watchdog dump всех потоков:

   ```sh
   BB_TIMEOUT=25 ./Bloodborne-bbport-x86_64-test-1016.AppImage --play > bbport-startup-watchdog.log 2>&1
   ```

   Ожидается завершение через 25 секунд после установки watchdog, с
   `STOP: watchdog timeout; thread stacks`. В отличие от приложенного GPU stall
   dump это включает главный поток, регистры, данные по указателям и stack words.
   Тест намеренно завершает этот запуск. Сохранения и настройки командой не меняются;
   сама игра может выполнять обычные записи своего запуска.

2. Для нулевого вызова сохранить полный linker trace, включая дочерний vulkaninfo:

   ```sh
   LD_DEBUG=libs,files __EGL_VENDOR_LIBRARY_FILENAMES=/usr/share/glvnd/egl_vendor.d/10_nvidia.json:/usr/share/glvnd/egl_vendor.d/50_mesa.json ./Bloodborne-bbport-x86_64-test-1016.AppImage --vulkan-info > bbport-nvidia-linker.log 2>&1
   ```

   Это reproducer без запуска игры. Нужны сообщения о неразрешённых символах и
   зависимостях непосредственно перед SIGSEGV. Повторение уже исключённых переключателей
   DLSS/async submit/memory model без новых данных не локализует этот сбой.

Локальная машина не имеет проприетарного NVIDIA ICD. На ней нельзя подтвердить
исправление этого драйверного пути или объявить проблему решённой.

## Дополнение: bb-loop.txt, bb-vals.txt и bb-hung.txt

Новые файлы существенно уточняют именно зависание без окна. Это не тот же
случай, что нулевой вызов из NVIDIA EGL core:

- Главный поток находится в обычном ограничителе частоты кадров:
  `+0x2034af0…+0x2034b6f`, вызывающем gettimeofday. В двух замерах через пять
  секунд меняются и текущее время, и начало кадра `[r12+0x20]`; цель ожидания
  составляет около 0.033333 секунды. Постоянное попадание профайлера сюда
  объясняется активным ожиданием между обновлениями, а не доказывает зависание часов.
- Ноль системных вызовов у этого потока совместим с gettimeofday через vDSO;
  это не означает, что время перестало обновляться.
- Цепочка `+0x1e4a6f5 ← +0x2018e27 ← +0x2034b35` соответствует внешнему
  игровому циклу, одному обновлению приложения и лимитеру соответственно.
- В watchdog GPU уже исполнил все 18 начальных команд, очередь пуста, метка
  достигла `0x11`. Это исключает ожидание исполнения именно этих команд,
  но не доказывает исправность всего пути последующего представления кадра.
- Ожидания спящих рабочих потоков сами по себе не устанавливают потерянное
  пробуждение: рабочие потоки также спят, когда главный цикл не выдаёт им задач.

### Что найдено в гостевом коде

Адреса ниже — смещения относительно базы образа `0x800000000`.

| Точка | Значение для диагностики |
| --- | --- |
| `+0x2018d20` | Обновление главного цикла |
| `+0x2018e27` | Возврат из лимитера, до передачи кадра диспетчеру |
| `+0x20512a0` → `+0xf88c60` → `+0xf88c70` | Путь обновления игровых задач |
| Глобальный указатель `+0x54b2e30` | Объект диспетчера |
| `dispatcher+0x38` | Если байт ненулевой при входе, диспетчер сразу возвращается; во время обычного вызова корневой задачи он временно равен 1 |
| `dispatcher+0x40` | Корневая задача; при ненулевом указателе вызывается её виртуальный метод `vtable+0x30` |
| Глобальный указатель `+0x5540518` | Таблица из 76 зарегистрированных игровых задач после указателя vtable |

Поэтому следующий замер надо делать на границе кадра, когда кратковременный
флаг выполнения не будет ошибочно принят за неисправность. В старом
`bbport-startup-watchdog.log` сохранены RIP/RDI и цепочки кадров, но нет этих
объектов. `bb-vals.txt` содержит объект лимитера, а не диспетчера. Определить
конкретное условие остановки загрузки по уже присланным файлам пока нельзя.

`SprjWindow` в этой сборке имеет метод опроса, который в конце вызывает
`+0xfe3960` и возвращает true. В runtime системный статус также всегда
foreground. Прямой зависимости этой части игрового цикла от фокуса SDL-окна
не обнаружено; подменять фокус или насильно показывать окно оснований нет.

### Прицельный замер без пересборки AppImage

Добавлен `scripts/diagnose_boot.gdb`. Он подходит к уже зависшему процессу,
проверяет сигнатуру гостевого кода, ставит временную точку останова на
`+0x2018e27`, снимает три состояния с интервалом восемь обновлений и
отсоединяется. Снимаются диспетчер, корневая задача с методом обновления,
таблица задач и объекты состояния. Скрипт не вызывает гостевые функции,
не меняет флаги и не пропускает инициализацию. Короткие остановки всех
потоков отладчиком временно влияют на тайминги.

Запустить игру обычным способом, дождаться зависания и из корня проекта
в другом терминале выполнить, подставив PID главного процесса bb-probe:

```sh
gdb -nx -q -batch -ex 'set auto-solib-add off' -p PID \
    -x scripts/diagnose_boot.gdb > bb-boot-state.txt 2>&1
```

Если attach сообщает `ptrace: Operation not permitted`, повторить эту же
команду с `sudo gdb`: ограничение Yama может запрещать подключение к соседнему
процессу того же пользователя. Отключать системное ограничение целиком не нужно.

Признак полного замера: `BOOT DIAGNOSIS COMPLETE`. Если отладчик не
достигает границы кадра, прервать Ctrl+C и сохранить полученный вывод;
скрипт при выходе удаляет свою точку останова и отсоединяется.
Нужен именно `bb-boot-state.txt`, чтобы сравнить состояние задач с рабочим
запуском. Уже проверенные переключатели GPU, memory model, FPS, аудио и TZ
повторять для этого замера не требуется.

Локальная проверка скрипта на рабочем запуске с отдельной копией сохранений
завершена: получены все три снимка, во всех `dispatcher+0x38=0`, корневая
задача существует, её метод обновления — `+0xf8a370`. Эталон сохранён в
`out/dev/boot-hang/reference-v2/bb-boot-state.txt`, полный лог — рядом,
`game.log`. Это проверка диагностического инструмента на текущей сборке
с AMD GPU, а не воспроизведение зависания на машине автора и не исправление.

## Попытки воспроизведения на локальной машине

По просьбе пользователя проверена именно старая
`dist/Bloodborne-bbport-x86_64-test-1016.AppImage`, а не только текущая сборка.
SHA-256 локального файла:
`9d5139e98f219cd227921b3fc642b5baf4bcb039bf32d686f148022bf2cd61b5`.
Совпадение хеша с файлом автора отчёта не проверялось.

Машина: Ryzen 7 5700X3D, Radeon RX 7800 XT, NixOS, ядро
`7.2.10-cachyos`, Hyprland 0.56.2. Каждый запуск использовал отдельный профиль;
основные настройки и сохранения пользователя не менялись. Общие параметры:
1920×1080, TAA, 30 FPS, DLSS выключен, SDL dummy audio, новая модель памяти.
Запуски последовательно завершались тестовым скриптом примерно через 36 секунд.

| Проверка | Окно появилось | Строк кадровой статистики | Результат |
| --- | --- | --- | --- |
| test-1016, Wayland | Да | 840 | Boot hang и Fault не воспроизвелись |
| test-1016, Wayland, affinity одного CPU | Да | 881 | Boot hang и Fault не воспроизвелись |
| test-1016, X11 через Xwayland | Да | 880 | Boot hang и Fault не воспроизвелись |
| test-1016, Wayland, пустой профиль | Да | 880 | Boot hang и Fault не воспроизвелись |
| test-1016, Wayland, пустой профиль, только Intel Black Tonemap Fix | Да | 880 | Boot hang и Fault не воспроизвелись |

Первые три запуска использовали копию сохранения и отключение пяти графических
эффектов; из общей папки также подхватился Sprint Fix. Четвёртый запуск убрал
настройки эффектов, но ещё подхватил Sprint Fix. В пятом внешние патчи исключены
через отдельный пустой каталог, а лог подтверждает ровно одну запись патча:
`FPS preset 30; 1 writes from ['Intel Black Tonemap Fix']`.

Во всех пяти случаях создан Core.Res.TaskManager, очередь прошла дальше
стартовых вычислений, окно появилось в списке mapped clients Hyprland, кадры
продолжались до остановки теста. Прямое чтение памяти процесса также подтвердило
существование диспетчера, корневой задачи и нулевой in_update при последнем замере.
Это не воспроизведение плавающей ошибки и не доказательство отсутствия гонки.

Результаты и полные логи:
`out/dev/boot-hang/local-matrix/summary.json`,
`out/dev/boot-hang/local-clean/summary.json`,
`out/dev/boot-hang/local-native/summary.json`.
На AMD нельзя проверить нулевой вызов именно внутри проприетарного NVIDIA EGL
core. Сходное зависание загрузки в принципе можно искать локально, поскольку
автор наблюдает его также на Intel GPU, но перечисленные варианты его не дали.

После обзора GitHub найден ещё один похожий отчёт:
[#216](https://github.com/deadinside28/bloodborne_pc/issues/216), RX 5500 XT,
лог тоже заканчивается после Core.Res.TaskManager. Там прежний renderer и нет
снимка главного потока, поэтому общая причина пока не установлена. PR #193
про низкие адреса потоков уже реализован в текущей линии; Windows boot-fix
из комментария к PR #138 относится к отдельной ошибке Windows-ветки автора.
Подробности и остальные актуальные PR:
[обзор GitHub](GitHub_review_2026-10-17.ru.md).
